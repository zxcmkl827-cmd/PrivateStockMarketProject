## 작업 목적

**2~3개월의 페이퍼 트레이딩 기간이 끝난 후, P4.1에서 기록한 로그를 분석하여 성공 기준을 판정**한다.

요구사항 7절의 성공 기준:
- **"해당 기간 중 실제 재고가 필요했던 하락 사례를 최소 1건 이상 모델이 놓치지 않고 잡아내는지 확인"**

즉, 다음과 같은 판정:
- **성공**: 관찰 기간 중 실제 심각한 하락이 있었던 종목에 대해, 시스템이 하락 전 또는 하락 초기에 경보를 냈으며, 사용자가 그 경보를 받고 손절/비중축소를 했다면 손실을 줄일 수 있었을 것이다.
- **미충족**: 실제 하락이 있었는데 시스템이 경보를 놓쳤다. 또는 기간 중 실제 하락 사례가 없어서 검증 불가.

미충족 시에는 P2로 회귀하여 로직을 재조정하고, 다시 페이퍼 트레이딩을 진행한다.

## 쉬운 설명

"2~3개월 동안 모은 데이터를 봐서, '우리 시스템이 실제 문제를 제때 잡았나?'를 평가하는 부분"이다.

예를 들어:
```
관찰 기간: 2026-09-15 ~ 2026-11-15 (2개월)

실제 하락 사례들 (사용자나 뉴스로 확인):
  1. AAPL: 10월 1일부터 -12% 하락 (명백한 문제)
  2. MSFT: 9월 28일부터 -8% 하락 (명백한 문제)
  3. TSLA: 9월 20일부터 -6% 하락 (약한 신호)

우리 시스템의 경보:
  1. AAPL: 9월 30일 [유지관찰] ← 하락 시작 1일 전! ✓
  2. AAPL: 10월 2일 [비중축소] ← 하락 후에도 계속 경보 ✓
  3. MSFT: 9월 25일 [유지관찰] ← 하락 3일 전! ✓
  4. MSFT: 9월 27일, 28일 [비중축소] ← 계속 경보 ✓
  5. TSLA: 경보 없음 ✗ (약한 신호라 놓침)

판정: "3개 문제 중 2개는 명확히 잡았고, 1개는 못 잡았다 → 부분 성공"
  → 기준 충족? 최소 1개 이상 성공 → YES ✓
  → 다음 단계: 실제 매매 반영 OK, 또는 로직 더 개선 권장
```

   ```python
   def analyze_paper_trading_results(start_date, end_date):
   ```

   ```python
   def identify_real_issues(start_date, end_date):
       # 관찰 기간 중 실제 심각한 하락이 있었던 종목들
       # 방법: 가격 데이터에서 -8% 이상 하락한 날이 있는가?
       
       my_stocks = ['AAPL', 'MSFT', 'COST', ...]
       real_issues = []

           max_drop = get_max_drawdown(ticker, start_date, end_date)
           if max_drop < -8:  # 8% 이상 하락

   ```

6. 성공 기준 판정 함수
   ```python
   def evaluate_success_criteria(start_date, end_date):
       real_issues = identify_real_issues(start_date, end_date)
       alerts = get_alerts_in_period(start_date, end_date)
       
       # 실제 문제 종목들이 시스템에 의해 경보되었는가?
       caught_issues = 0
       for issue in real_issues:
           ticker = issue['ticker']
           
           # 이 종목에 대해 하락 이전에 경보가 있었는가?
           relevant_alerts = [a for a in alerts 
                            if a['ticker'] == ticker 
                            and a['date'] < issue['bottom_date']]
           
           if relevant_alerts:
               caught_issues += 1
       
       success_rate = caught_issues / len(real_issues) if real_issues else 0
       
       return {
           'real_issues_count': len(real_issues),
           'caught_count': caught_issues,
           'success_rate': success_rate,
           'passed': caught_issues >= 1  # 성공 기준: 최소 1개 이상
       }
   ```

7. 최종 리포트 생성

   ```python
   def generate_final_report(start_date, end_date):

       1. 실제 문제 사례: {result['real_issues_count']}개

       다음 단계:
       {'- 실제 매매에 반영 가능' if result['passed'] else '- P2로 회귀하여 로직 재조정 필요'}
   ```

## Done-when 확인 방법

백로그의 done_when: **"성공 기준(재고가 필요했던 하락 사례를 최소 1건 이상 놓치지 않음) 충족 여부가 사용자 확인과 함께 기록됨. 미충족 시, 재조정이 필요한 신규 작업을 backlog_cli.py add로 등록하고 그 id를 이 작업의 log에 기록"**

Gate 조건 (신규 추가): **사용자 확인 근거(충족/미충족 판단과 일자)가 log에 기록되어 있을 것**

확인 방법:

1. **최종 리포트 생성 확인**:
   - 리포트가 생성되었는가?
   - 다음 내용이 포함되어 있는가?
     - 관찰 기간 (시작일 ~ 종료일)
     - 실제 문제 사례 개수
     - 시스템이 감지한 사례 개수
     - 성공률 또는 정성적 평가

2. **성공 기준 판정**:
   - 리포트에 "성공 기준 충족" 또는 "미충족"이 명시되어 있는가?
   - 근거가 명확한가? (예: "3개 문제 중 2개 감지 → 통과" 또는 "2개 문제 중 0개 감지 → 불통과")

3. **사용자 확인** (Gate 조건):
   - 사용자가 최종 리포트를 검토했는가?
   - 사용자의 확인 서명, 판단 일자, 판단 근거가 log에 기록되어 있는가?
   - 예: "2026-11-15, 사용자 확인: 성공 (2개 문제 중 2개 감지)"

4. **다음 단계 결정**:
   - 성공 기준 충족 시:
     - "실제 매매에 반영 가능"
     - P5(운영 단계)로 진행 (또는 프로젝트 완료)
   - 미충족 시:
     - 신규 작업 등록: `backlog_cli.py add` 명령으로 "P2 재조정" 작업 생성
     - 그 신규 작업의 ID를 이 작업(P4.2)의 log에 기록
     - 예: "2026-11-15, 미충족 판정 → 신규 작업 P2.5 등록"
     - P2의 status를 `in_progress`로 변경
     - 개선 방향 상세 기록

5. **문서 보존**:
   - 최종 리포트를 `docs/paper_trading_report_2026-09-15_to_2026-11-15.md` 같은 형태로 저장
   - 향후 기준으로 참고할 수 있도록 기록
   - Gate 조건 만족: 사용자 확인 근거, 신규 작업 ID(미충족 시) 등이 명시되어 있는가?

6. **개선 사항 분석** (선택사항, 미충족 시 필수):
   - 놓친 사례: 왜 경보를 안 냈는가? (임계값이 너무 높은가? 뉴스 감지 미흡?)
   - 오탐 사례: 왜 잘못된 경보를 냈는가?
   - P2 개선 제안 기록
