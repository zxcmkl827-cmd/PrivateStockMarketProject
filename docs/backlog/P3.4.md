## 작업 목적

스캔 1회당 여러 종목에서 알림이 발생했을 때, 현재의 "종목마다 개별 카카오톡/이메일 메시지 발송" 방식을 **"모든 알림 대상을 등급 우선순위(매도>비중축소>유지관찰)로 정렬한 뒤, 길이 제약에 맞춰 필요시 자동 분할하되 하나 이상의 통합 메시지로 발송"** 하도록 변경한다.

더 나아가, **발송 실패가 당일 스캔 로그 전체를 유실하는 일을 방지**하고, **"매도" 등급 알림이 다른 등급에 묻히지 않도록 가시성을 확보**하는 것이 핵심이다.

요구사항 문서(§3.4 알림 등급과 판단 기준)에서 강조한 대로, "매도" 알림의 신중성과 가시성은 프로젝트의 설계 원칙이기 때문에, 이 작업에서 그 원칙을 코드 수준에서 구현해야 한다.

## 쉬운 설명

기존: 스캔 결과 알림 3개가 나오면 → 카카오톡/이메일 메시지 3개를 따로 발송
변경: 스캔 결과 알림 3개가 나오면 → 등급 우선순위대로 정렬 → 1개 또는 여러 메시지로 통합 발송 (메시지 길이 초과 시에만 분할)

**추가 개선**:
1. **발송 실패 시에도 당일 스캔 로그는 항상 남음** — 예외가 로그 기록 코드를 막지 않도록 처리
2. **"매도" 등급이 항상 앞쪽(첫 청크)에 배치** — 여러 메시지가 필요한 경우에도 중요한 알림을 놓치지 않음
3. **발송 상태와 결과를 로그에 명확히 기록** — 어떤 채널이 성공/실패했는지, 몇 개 메시지를 발송했는지 추적 가능

## 필요한 입력

- **P3.2 완료**: 카카오톡/이메일 발송 함수(`send_notification()`)가 이미 구현되어 있어야 함
- **P3.1 또는 그 이전 작업**: 등급별 메시지 생성 로직

  - `app/notify_format.py` (메시지 포맷팅, 이미 존재하거나 이 작업에서 생성)

## 결과물

### 1. `app/notify_format.py` — 통합 메시지 생성 함수 (수정/신규)

```python
def format_combined_alert_message(
    alerts: list[tuple[str, str]],  # (등급, 메시지) 튜플 리스트
    max_chars: int = SAFE_MESSAGE_LENGTH  # 메시지 길이 제약
) -> list[str]:
```

- **입력**: `(등급, 메시지)` 튜플 리스트. 등급은 `매도`, `비중축소`, `유지관찰` 중 하나.
- **동작**:
  1. 입력 리스트를 `GRADE_PRIORITY` 기준으로 정렬 (매도: 0, 비중축소: 1, 유지관찰: 2)
  2. 정렬된 메시지를 순서대로 모음 → 길이 초과 시 새 청크로 분할
  3. 각 청크마다 헤더 추가: `"[추세 이탈 알림] 총 N건 (매도 a건, 비중축소 b건, 유지관찰 c건)"`
  4. 청크 2개 이상이면 각 메시지 끝에 `"- i/전체청크수"` 표시
- **출력**: 메시지 문자열 리스트 (`list[str]`)
- **상수**: `SAFE_MESSAGE_LENGTH = 900` (카카오톡 정확한 한도는 미확인이나, 보수적 안전 마진으로 900자 설정)

### 2. `app/main.py` — `_grade_ticker()` (수정)

- **변경점**: 더 이상 이 함수 내부에서 `send_notification()` 호출 안 함
- **반환값**: `(grade, message)` 형태로, 등급과 메시지를 tuple로 반환
- **역할**: 단순히 "이 종목이 어떤 등급의 알림인가, 메시지는 무엇인가"만 결정

### 3. `app/main.py` — `run_scan()` (수정)

**핵심 변경**:
1. **메시지 수집 단계**: 각 종목을 순회하며 `_grade_ticker()`로 메시지를 수집, 리스트에 추가
2. **통합 단계**: 모든 메시지를 수집한 후 `format_combined_alert_message()`로 통합
3. **발송 단계**: 통합 메시지 리스트의 각 항목을 순회하며 `send_notification()` 호출 (각각을 `try/except`로 감쌈)
4. **로그 기록 단계**: 발송 성공/실패와 무관하게, 루프 끝에서 당일 스캔 로그를 `scan_log.jsonl`에 **반드시 기록**

```python
def run_scan():
    alert_items = []  # (grade, message) 튜플 수집
    
    for ticker in tickers:
        result = _grade_ticker(ticker)
        if result.get("grade"):
            alert_items.append((result["grade"], result["message"]))
    
    # 통합 메시지 생성
    if alert_items:
        messages_to_send = format_combined_alert_message(alert_items)
    else:
        messages_to_send = []
    
    # 발송 (각각을 독립적으로 처리)
    notification_channels = []
    notification_errors = []
    for msg in messages_to_send:
        try:
            channels = send_notification(msg)
            notification_channels.extend(channels)
        except Exception as e:
            notification_errors.append(str(e))
    
    # 로그 기록 (발송 성공/실패와 무관하게 항상 실행)
    record = {
        "date": TODAY,
        "grades": [g for g, _ in alert_items],
        "reasons": [...],
        "notification_channel": ",".join(notification_channels) if notification_channels else "NONE",
        "notification_error": ";".join(notification_errors) if notification_errors else "NONE",
        "notification_message_count": len(messages_to_send),
        ...
    }
    with open(LOG_PATH, "a") as f:
        f.write(json.dumps(record) + "\n")
```

**로그 필드 추가**:
- `notification_channel`: 성공한 채널 (카카오톡/이메일 등), 쉼표 구분
- `notification_error`: 발송 중 발생한 에러 메시지, 세미콜론 구분
- `notification_message_count`: 실제 발송한 청크 수 (0 = 알림 없음, 1 = 길이 안 초과, 2 이상 = 자동 분할)

### 3. 통합 메시지 포맷 확인

생성된 메시지가 다음을 포함해야 함:

- [x] 헤더: `"[추세 이탈 알림] 총 N건 (매도 a건, 비중축소 b건, 유지관찰 c건)"`
- [x] 메시지들 사이에 빈 줄로 구분
- [x] 등급 우선순위 준수 (매도 → 비중축소 → 유지관찰 순)
- [x] 청크 2개 이상이면 각 끝에 "- i/총청크수" 표시

```
가격: -6.1% (최근 2주)
뉴스: 공급망 지연
시장: S&P500 +0.2% (종목 고유 문제)
→ 비중 축소 고려

[유지관찰] AAPL
가격: -4.8% (최근 2주)
뉴스: 특별한 부정 신호 없음
시장: S&P500 -2.8% (시장 조정)
→ 주시 권장
```

### (1) 발송 실패 시 scan_log 유실 — 해결됨

**문제**: 이전에는 `send_notification()` 호출이 예외를 던지면, 로그 기록 코드까지 도달하지 못해 그날의 스캔 레코드가 통째로 유실될 수 있었음.

**해결책**:
- `run_scan()` 함수에서 발송 로직을 모두 `try/except`로 감쌈
- 발송 루프 이후에 로그 기록 코드를 배치하여, 발송 성공/실패와 무관하게 항상 실행됨
- 로그에 `notification_error` 필드로 발송 중 발생한 에러를 기록하되, 이것이 로그 기록 자체를 막지 않음

**확인 방법**:
- `app/main.py`의 `run_scan()` 함수 말미를 검사
- 발송 루프가 모두 `try/except`로 감싸져 있는가?
- 로그 기록(`scan_log.jsonl` 쓰기) 코드가 발송 루프 이후에 있는가?
- 발송 실패 시에도 로그가 남는지 테스트 (모킹 또는 실제 네트워크 차단)

### (2) 통합 메시지 길이 초과로 인한 발송 실패/절단 — 해결됨

**문제**: 알림이 많거나 텍스트가 길면 통합 메시지가 카카오톡 또는 이메일의 길이 제약을 초과하여 발송 실패 또는 내용 절단 가능성.

**해결책**:
- `format_combined_alert_message()` 함수에서 `max_chars` 매개변수를 받아 길이 제약 설정 (기본값 `SAFE_MESSAGE_LENGTH = 900`)
- 정렬된 메시지를 순서대로 이어붙이다가 길이를 초과하면, 새 청크로 분할
- 등급 우선순위는 청크 간에도 유지 (즉, 매도는 항상 첫 청크)
- 각 청크에 독립적인 헤더와 청크 번호 표시로, 여러 메시지로 받아도 맥락을 명확히 함

**확인 방법**:
- `app/notify_format.py`의 `SAFE_MESSAGE_LENGTH` 상수 확인 (900)
- 길이 초과 시 분할 로직 검사 (문자 수 계산 및 새 청크 추가)
- 각 청크의 헤더에 "총 N건" 요약이 있는가? (각 청크마다 재계산)
- 청크 2개 이상일 때 "i/전체청크수" 표시가 있는가?

**미확인사항**:
- 카카오톡의 정확한 길이 한도는 외부 API 문서에서 공식 확인하지 않음
- SAFE_MESSAGE_LENGTH=900은 보수적 추정치
- 사용자가 실측 검증을 하지 않기로 확정함 (2026-09-15): "실측 없이 자동분할 방식으로 진행" → 따라서 `done_when` 충족에는 실측이 필요 없음

### (3) 매도 등급이 유지관찰 더미에 묻히는 문제 — 해결됨

**문제**: 이전에는 메시지들의 순서가 정렬되지 않아, "매도(가장 신중해야 할 알림)"가 여러 "유지관찰" 메시지 사이에 묻혀 가시성이 떨어질 수 있음.

**해결책**:
- `format_combined_alert_message()` 함수에서 입력받은 `(등급, 메시지)` 튜플 리스트를 `GRADE_PRIORITY` 기준으로 정렬
- 매도(0) → 비중축소(1) → 유지관찰(2) 순으로 정렬되므로, 매도가 항상 맨 앞에 오고, 길이 초과로 분할되더라도 첫 청크에 포함됨
- 메시지 헤더에 "총 N건 (매도 a건, 비중축소 b건, 유지관찰 c건)" 요약을 추가하여, 사용자가 한눈에 각 등급의 개수를 파악 가능

**확인 방법**:
- `app/notify_format.py`에서 정렬 로직 검사 (`GRADE_PRIORITY` 기준 `sorted()`)
- 등급 순서 테스트: 유지관찰/비중축소/매도를 섞은 입력 → 매도가 첫 메시지에 나타나는지 확인
- 길이 분할 후에도 매도 메시지가 첫 청크에 있는지 확인
