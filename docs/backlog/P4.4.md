## 작업 목적

이 프로젝트는 매일 알림을 발생시키고, 각 알림 시점의 가격·뉴스·근거를 `scan_log.jsonl`에 기록한다. 이후 1주/2주 후 종가로 사후 검증하여 판단 정확도를 평가하고, 근거 유형별 가중치를 자동 조정한다(요구사항 5.8).

현재 이 모든 데이터는 로컬 JSONL 파일(`scan_log.jsonl`, `feedback_report.jsonl`, `weight_adjustments.jsonl`)에만 저장되어 있다. 이들 파일은 행 단위로 누적되는 로그 형식이라서, 특정 기간의 적중률을 집계하거나 근거별로 필터링하여 분석하려면 매번 파일을 파싱해야 한다.

**P4.4의 목적**은 이 조회·집계 작업을 쉽게 하기 위해 Supabase(관계형 데이터베이스, PostgreSQL 백엔드)를 **보조 미러**로 추가하는 것이다. 로컬 JSONL은 여전히 1차 진실 공급원으로서 모든 시스템 로직에 사용되고, Supabase는 그 사본을 조회/집계 편의용으로만 유지한다.

## 쉬운 설명

매일 스캔 결과를 저장하고, 후에 "지난달 내 예측이 얼마나 맞았나?"를 집계하려면:
- **현재(JSONL)**: 로컬 파일을 직접 열어서 손으로 필터링·계산 필요
- **미래(Supabase 미러 추가 후)**: 클라우드 데이터베이스에 쿼리하면 결과 테이블이 바로 나옴

예를 들어 "가격 하락 신호가 몇 번 발생했고, 그 중 정확히 맞은 건 몇 개인가?" 같은 질문에 대해:
- 지금: JSONL 로그를 읽어서 Python으로 파싱·필터링
- 미래: SQL 한 줄로 `SELECT COUNT(*) FROM scan_log WHERE basis = 'price_decline' AND accuracy = 'hit'` 실행

단, **중요한 원칙**: Supabase 업로드가 실패해도 시스템은 계속 작동해야 한다. 로컬 기록이 완료되면 알림을 바로 보내고, 매매 판단에도 영향을 주면 안 된다. Supabase는 배경에서 조용히 실패해도 괜찮은 "best-effort" 보조 기능이다.

## 결과물

이 작업이 끝나면 다음이 완성된다:

1. **Supabase 테이블 설계**: 로컬 JSONL 3종(scan_log, feedback_report, weight_adjustments)에 대응하는 PostgreSQL 테이블 3개 설계 및 생성. 각 테이블은 JSONL 행을 구조화한 컬럼으로 표현.
2. **스캔 스크립트 통합**: `app/main.py`의 매일 자동 스캔 실행 흐름에 Supabase 업로드 함수 추가. 로컬 JSONL 기록이 완료된 직후, 그 데이터를 Supabase 테이블에 `INSERT`하는 로직.
3. **환경변수 설정 파일**: Supabase URL·API 키를 외부 설정(`.env` 또는 Windows 환경변수)에서 로드하는 코드. 코드 저장소에는 하드코딩되지 않음.
4. **에러 격리**: Supabase 업로드 함수가 실패해도 `try-except`로 감싸서, 그 실패가 로컬 기록·알림 발송·가중치 조정 로직에 영향을 주지 않도록 격리.
5. **보안 검토**: Supabase MCP 도구(`mcp__supabase__get_advisors`)로 생성된 테이블·인증 방식의 보안 권고사항 확인. 심각한 미해결 항목 없음을 확인서에 기록.

이 작업을 진행할 때 추천 순서:

2. **Supabase 테이블 설계**:
   - 로컬 JSONL 파일 3종을 현재 코드에서 열어보고, 각각의 컬럼 구조(필드명·타입)를 파악.

     - `scan_log` 테이블: scan 시각, 종목명, 가격 변화, 감지 등급, 적용된 가중치, 근거 유형 등을 컬럼으로 구성
     - `feedback_report` 테이블: 원본 알림 시각, 사후 검증 시각, 알림 후 가격 변화, 적중/과잉감지 판정
     - `weight_adjustments` 테이블: 근거 유형, 기존 가중치, 조정된 가중치, 적중률, 표본수, 조정 시각
   - **확인 질문**: 각 JSONL 파일의 정확한 필드 목록과 타입은 코드를 직접 확인해야 하므로, 이 문서 작성 시점에는 추측만 가능. 실제 구현 시 코드를 열어 필드를 파악해야 한다.

3. **환경변수 설정**:

   - 코드에는 "os.getenv('SUPABASE_URL')" 같은 호출만 남기고, 실제 키는 저장소에 커밋하지 않음.

4. **업로드 함수 구현**:
   - `app/` 폴더(또는 별도 유틸 모듈) 안에 `supabase_mirror.py` 같은 파일을 만들어, 로컬 JSONL을 읽고 Supabase에 `INSERT`하는 함수 작성.
   - 각 JSONL 파일(scan_log, feedback_report, weight_adjustments)에 대해 별도 함수 또는 통합 함수로 구현. 설계는 리뷰어 및 주체가 결정.

5. **스캔 스크립트 통합**:
   - `app/main.py`의 매일 자동 스캔 실행 흐름을 열어, 로컬 JSONL 기록이 완료된 직후 위의 업로드 함수를 호출하도록 추가.

   - **호출 위치**: 로컬 기록 직후이고, 알림 발송 전 또는 후인지는 설계에 따라 다를 수 있음. 단, 알림/가중치 조정 로직과는 분리되어 있어야 함.

## done_when 확인 방법

백로그의 `done_when` 필드에 명시된 5개 판정 기준과 그것을 실제로 확인하는 방법:

### 1. **Supabase 연결 정보가 환경변수로만 관리됨**
- **백로그 표현**: "Supabase 연결 정보(프로젝트 URL/키)가 환경변수로만 관리되고 저장소에 하드코딩되지 않음을 코드로 확인"
- **확인 방법**:
  - `app/` 폴더의 Supabase 업로드 함수가 포함된 파일을 열어서, Supabase URL과 API 키를 로드하는 코드 확인.
  - `os.getenv('SUPABASE_URL')` / `os.getenv('SUPABASE_ANON_KEY')` 같은 호출이 있는지 확인.
  - 저장소 내의 모든 `.py` 파일(및 설정 파일)에 `https://` 로 시작하는 Supabase URL이나 `eyJ...` 형태의 키 문자열이 하드코딩되어 있지 않은지 grep/검색으로 확인.
  - `.gitignore`에 `.env` 파일이 등재되어 있는지 확인 (환경변수 파일이 커밋 대상에서 제외되는지).

### 2. **Supabase 테이블 3개 설계 및 오늘자 레코드 적재 확인**
- **백로그 표현**: "app/main.py 스캔 실행 흐름에서 scan_log.jsonl/feedback_report.jsonl/weight_adjustments.jsonl 각각에 대응하는 Supabase 테이블 3개가 설계되고, 실제 실행으로 각 테이블에 오늘자 레코드가 적재됨을 확인"
- **확인 방법**:
  - Supabase 웹 대시보드(https://app.supabase.com)에 로그인해서, 해당 프로젝트의 "SQL Editor" 또는 "Table Editor" 탭에서 아래 3개 테이블이 존재하는지 확인:
    - `scan_log` (또는 유사 명칭)
    - `feedback_report` (또는 유사 명칭)
    - `weight_adjustments` (또는 유사 명칭)
  - 각 테이블을 클릭해서, 컬럼 구조(필드명·타입)가 로컬 JSONL 데이터와 대응되는지 확인. 예를 들어 scan_log 테이블이 "stock", "price_change", "alert_level", "timestamp" 같은 컬럼을 가지고 있는지.
  - 오늘(2026-09-16) 또는 최근 실행일의 데이터가 각 테이블에 적재되어 있는지 확인. 예: `SELECT COUNT(*) FROM scan_log WHERE DATE(created_at) = CURRENT_DATE` 쿼리로 오늘자 행 개수 확인. 최소 1건 이상 있어야 함.
  - 또는 Python REPL/스크립트에서 MCP 도구 `mcp__supabase__select_all`을 사용해 각 테이블의 최근 행 조회.

### 3. **Supabase 업로드 실패 시 로컬 흐름 정상 동작 확인**
- **백로그 표현**: "Supabase 업로드 함수를 강제 실패시킨 상태에서 로컬 JSONL 기록·등급 판정·알림 발송이 정상 동작함을 실측으로 확인(업로드는 로컬 흐름과 분리된 best-effort여야 함)"
- **확인 방법**:
  1. 테스트용 코드 수정: Supabase 업로드 함수 내에 `raise Exception("Forced failure for testing")` 또는 잘못된 URL 설정을 임시로 추가.
  2. 매일 자동 스캔 스크립트(`python3 app/main.py` 또는 수동 실행)를 실행.
  3. 실행 후 다음을 확인:
     - 로컬 JSONL 파일들(`data/logs/scan_log.jsonl`, `data/logs/feedback_report.jsonl` 등)에 새 행이 추가되었는가? (`tail` 명령으로 마지막 몇 줄 확인)
     - 등급 판정이 정상적으로 이루어졌는가? (scan_log.jsonl에 alert_level 필드가 올바르게 기록되었는가?)
     - 알림이 발송되었는가? (스캔이 필요한 신호를 감지했다면 카카오톡이나 이메일을 받았는가? 또는 로그에 "Notification sent" 메시지가 있는가?)
  4. 로그(예: `data/logs/scan_log.jsonl`)를 직접 열어서 "upload to supabase failed" 같은 로그 라인이 있어도 그 다음 행에서 정상 처리가 계속되는지 확인.
  5. 테스트 후 강제 실패 코드는 제거.

### 4. **Supabase 보안 권고사항 확인**
- **백로그 표현**: "mcp__supabase__get_advisors로 보안 권고사항을 확인해 심각한 미해결 항목이 없음을 확인"
- **확인 방법**:
  - MCP 도구 `mcp__supabase__get_advisors`를 호출(정확한 호출 방식은 프로젝트의 MCP 도구 문서 참고, 또는 호출자의 리뷰 시점에 지시).
  - 반환된 권고사항 목록을 읽어 심각도 분류.
  - 심각도 "HIGH" 또는 "CRITICAL"로 표시된 항목 중 "미해결" 상태(아직 조치하지 않은)인 항목이 없는지 확인.
