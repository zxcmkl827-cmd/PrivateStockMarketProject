## 작업 목적

이 프로젝트는 CLAUDE.md에 명시된 대로 "상시 대시보드보다는 알림 중심"이라는 원칙을 따른다. 일일 자동 스캔 후 이상이 감지되면 카카오톡/이메일 알림을 보내고, 이후 1주/2주 후 사후 검증 피드백을 수집해 판단 정확도를 평가한다(요구사항 5.8).

사용자는 매일 수신하는 알림으로 종목을 모니터링하면서, 동시에 "지난 한 달간 우리 시스템의 예측 정확도가 얼마나 되었나?" 또는 "특정 종목의 과거 신호들이 정말 맞았나?"를 사후에 읽어보고 싶어할 수 있다. 현재는 로컬 JSONL 파일(`scan_log.jsonl`, `feedback_report.jsonl`)이 원본이므로, 이들을 직접 분석하거나 Python으로 파싱해야만 이 정보를 볼 수 있다.

**P4.5의 목적**은 이 요구를 충족하기 위해 **사후 열람 전용 정적 웹 페이지**를 만들어 Vercel(또는 다른 정적 호스팅)에 배포하는 것이다. 사용자는 필요할 때 언제든 이 페이지에 접속해 스캔 이력, 피드백 결과, 정확도 통계를 웹 UI로 조회할 수 있다. 단, 이 페이지는 **읽기 전용**이며, 시스템의 알림 발송이나 등급 판정 로직과는 전혀 무관하다.

## 쉬운 설명

- **현재**: 로컬 JSONL 파일이 존재하지만, 이를 보려면 코드를 짜거나 텍스트 에디터로 직접 열어야 한다.
- **미래**: 간단한 URL(예: `https://review.myalerts.vercel.app/`)을 열면 지난 알림과 정확도 통계를 시각화된 표와 차트로 볼 수 있다.
- **예시**:
  - "최근 30일간 스캔한 종목 목록과 각각의 예측 정확도" 테이블
  - "가격 하락 신호가 가장 정확도가 높은 신호 유형인가?" 비교 차트
  - "9월 15일 AAPL에 대해 발송한 알림과, 1주 후 종가 결과, 최종 적중 여부" 기록
  - "매도 등급 알림의 적중률은 얼마나 높은가?" 통계

이 페이지는 **사용 후 평가용**이며, 실시간으로 갱신되지 않고 며칠 또는 주 단위로 배포가 갱신될 수 있다(또는 매일 자동 갱신, 설계에 따라 다름).

## 필요한 입력

이 작업을 시작하려면 다음이 준비되어야 한다:

1. **선행 작업 P4.4 완료**: P4.4에서 Supabase 미러링이 완성되고, 로컬 JSONL 데이터가 Supabase 테이블에 동기화되고 있을 것. 이 리뷰 페이지는 로컬 JSONL을 직접 읽지 않고 Supabase(조회 전용 키)만 바라본다.

2. **Supabase 테이블 스키마 확정**: P4.4에서 설계된 `scan_log`, `feedback_report`, `weight_adjustments` 테이블의 정확한 컬럼 구조 확인.

3. **Vercel 계정 및 프로젝트 준비** (선택적이나 권장):
   - Vercel 계정이 있고, GitHub 저장소와 연동 가능할 것.
   - 정적 사이트 호스팅 환경이 준비되어 있을 것 (또는 다른 정적 호스팅 서비스).

4. **API 클라이언트 라이브러리**: Supabase 공개(조회 전용) 키로 읽기 쿼리를 보낼 수 있는 JavaScript/TypeScript 클라이언트 라이브러리(예: `@supabase/supabase-js`).

5. **공개 범위 확정**: 저장소가 이미 Public이고 `scan_log.jsonl`/`feedback_report.jsonl`이 이미 커밋되어 공개 상태이므로, 동일 데이터를 웹 페이지로 보여주는 것은 새로운 공개 범위 확대가 아님을 확인.

## done_when 확인 방법

백로그의 `done_when` 필드에 명시된 5개 판정 기준과 그것을 실제로 확인하는 방법:

### 1. **P4.4가 done 상태**
- **백로그 표현**: "P4.4가 done 상태"
- **확인 방법**:
  - `python3 scripts/backlog_cli.py get P4.4`를 실행해 P4.4의 상태가 `done`인지 확인.
  - P4.4가 `in_progress` 또는 다른 상태라면 먼저 P4.4를 완료해야 함.

### 2. **페이지가 Supabase 조회 전용 키만 사용하고 쓰기 권한 키가 코드/번들에 노출되지 않음을 확인**
- **백로그 표현**: "페이지가 Supabase 조회 전용 키만 사용하고 쓰기 권한 키가 코드/번들에 노출되지 않음을 확인"
- **확인 방법**:
  - 배포된 페이지의 소스 코드(JavaScript 포함) 및 번들을 검사해서 `supabase_url`과 `supabase_anon_key` 같은 환경변수 로드 코드만 있는지 확인.
  - 실제 API 키 값(예: `eyJ...` 형태)이 코드에 하드코딩되어 있지 않은지 grep/검색으로 확인.
  - Supabase 프로젝트 대시보드에서 해당 키(Anon Key)의 권한 설정을 확인해, 읽기만 허용되고 쓰기/수정/삭제는 불가능한지 검증.
  - 네트워크 탭(브라우저 개발자 도구)에서 실제 Supabase API 호출을 모니터링해, 요청이 SELECT 쿼리만 포함하고 INSERT/UPDATE/DELETE는 없는지 확인.

### 3. **스캔 로그/피드백 리포트/가중치 조정 이력 3종이 실제 배포된 페이지에서 조회됨을 실측 확인**
- **백로그 표현**: "스캔 로그/피드백 리포트/가중치 조정 이력 3종이 실제 배포된 페이지에서 조회됨을 실측 확인"
- **확인 방법**:
  - 배포된 URL(예: Vercel 주소)에 접속.
  - 다음 3개 섹션이 페이지에 표시되는지 확인:
    1. **스캔 로그**: 최근 스캔 이력 (종목, 스캔 날짜, 감지 등급, 신호 유형 등)을 표시하는 테이블 또는 목록
    2. **피드백 리포트**: 사후 검증 결과 (원본 알림 날짜, 사후 검증 날짜, 결과 및 적중/과잉감지 판정)를 표시
    3. **가중치 조정 이력**: 근거 유형별 가중치가 어떻게 조정되었는지 (근거 유형, 기존 가중치, 조정된 가중치, 적중률, 조정 시각 등)
  - 각 섹션에서 실제 데이터(최소 1건 이상)가 표시되는지 확인. 예를 들어 스캔 로그에 최근 며칠간의 스캔 기록이 보이는지, 피드백 리포트에 최근 검증 결과가 보이는지.
  - 필터/소트 기능(있다면)을 시도해서 정상 작동하는지 확인.

### 4. **실시간 자동 갱신·푸시 알림 등 상시 대시보드 기능이 없음을 코드 리뷰로 확인**
- **백로그 표현**: "실시간 자동 갱신·푸시 알림 등 상시 대시보드 기능이 없음을 코드 리뷰로 확인"
- **확인 방법**:
  - 페이지 코드(HTML/JavaScript)를 열어서 다음을 검증:
    1. **WebSocket이나 setInterval로 자동 갱신하지 않음**: `ws://`, `WebSocket`, `setInterval`, `setTimeout`을 통한 주기적 리로드가 없는지 grep/검색으로 확인.
    2. **푸시 알림 라이브러리 없음**: `push`, `notification`, `serviceWorker` 등의 키워드가 알림 목적으로 사용되지 않는지 확인.
    3. **사후 열람 방식 유지**: 페이지 로드 시 Supabase에서 데이터를 1회 조회하고, 사용자가 수동으로 새로고침(F5)하기 전까지 갱신되지 않는 구조인지 확인.
  - Vercel 또는 빌드 설정에서 배포 빈도가 "매일 1회" 또는 "수동 배포"로 설정되어 있는지 확인 (자동 갱신이 아님).

### 5. **quality_check.py --scope full 통과**
- **백로그 표현**: "quality_check.py --scope full 통과"
- **확인 방법**:
  - 터미널에서 `python3 scripts/quality_check.py --scope full` 명령 실행.
  - 명령이 종료되고, 반환 코드가 0(성공) 또는 모든 항목이 "PASS" 상태인지 확인.
  - 만약 실패가 있다면 에러 메시지를 읽고 코드를 수정한 후 재실행.
  - P4.5 구현 코드(HTML/JavaScript)가 포함된 파일이 프로젝트의 코드 구조 규칙(파일 길이, lint, 빌드 안전성 등)을 만족하는지 검증.

  이는 CLAUDE.md의 "작업 실행 순서" 절 5번에 명시된 대로, 이 작업이 공개 페이지 배포라는 백로그 구조·정책에 영향을 주므로(사용자 공개 인터페이스 추가) `critical-reviewer` 서브에이전트의 검토를 받아야 한다는 의미다. 검토 후 지적 사항(보안 문제, 요구사항 이탈, 아키텍처 우려 등)이 있으면 반영하고, 그 반영을 실측으로 확인해야만 최종 `done` 처리가 가능하다.

## 명시적으로 배제되는 기능

이 작업에서는 다음을 **절대 구현하지 않는다**:

1. **실시간 자동 갱신**: 페이지를 열었을 때 1초마다 새로고침되는 대시보드 NO. 사후 열람 전용이므로 하루 1회 또는 필요시만 배포 갱신.
2. **푸시 알림 또는 배지 알림**: "새로운 피드백이 올렸습니다" 같은 활성 알림 기능 NO. (주 알림은 이미 카카오톡/이메일로 별도 처리)
3. **상시 모니터링 대시보드 성격**: 투자자가 "지금 이 종목이 어떤 상태인가"를 확인하는 용도 NO. 그것은 알림 채널의 역할. 이 페이지는 "지난주에 발송한 알림들이 얼마나 정확했나"를 회고하는 용도만.
4. **가격 실시간 업데이트**: 페이지 새로고침 없이 주가가 실시간으로 변경되는 기능 NO.
5. **등급 판정 로직 또는 신호 생성**: 이 페이지는 읽기 전용이며, 알림 발송이나 등급 판정에는 관여하지 않음.

## 공개 범위 및 보안 근거

**Q: 사용자의 개인 투자 종목을 공개적으로 표시하는 것 아닌가?**

A: 저장소 `zxcmkl827-cmd/PrivateStockMarketProject`는 이미 **Public**으로 설정되어 있으며, `scan_log.jsonl`과 `feedback_report.jsonl`이 이미 최신 커밋에 포함되어 있다. 즉, 누구든 저장소를 클론해서 이 JSONL 파일들을 직접 읽을 수 있는 상태다. 따라서 동일 데이터를 웹 페이지로 시각화해 보여주는 것 자체는 **새로운 공개 범위 확대가 아니다**.

다만, 다음의 보안 조건을 지켜야 한다:
- **Supabase 조회 전용 키만 사용**: 쓰기/수정/삭제 권한이 없는 공개 키로 제한.
- **RLS 정책 확인**: Supabase 테이블에 Row Level Security가 적절히 설정되어 있다면 추가 보호 가능 (옵션).
- **민감 정보 필터링**: 페이지에서 표시하는 데이터는 "스캔 이력, 피드백 결과, 정확도" 수준으로 제한하고, 가중치 조정 로직이나 내부 파라미터는 노출하지 않음.
